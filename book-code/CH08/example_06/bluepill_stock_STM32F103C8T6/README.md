# example_06 Rust inside a Zephyr application (Blue pill)

Zephyr keeps the main thread, the GPIO driver, and the build; Rust supplies one pure-logic function, `led_pattern()`. A Kconfig option, `CONFIG_LED_PATTERN_RUST`, selects between the Rust implementation and the original C one, so the migration can be reverted without editing any source.

The LED shows two short flashes followed by a longer pause, repeating about every two seconds.

The Rust build gives two flashes; changing the match arm to `0 | 2 | 4` gives three, with no C edits; rebuilding with `-DCONFIG_LED_PATTERN_RUST=n` returns to two flashes from the C fallback.

## Files

| Path | Purpose |
| --- | --- |
| `CMakeLists.txt` | Adds `main.c`, then either the Rust archive (`=y`) or `src/led_pattern.c` (`=n`) |
| `Kconfig` | Declares `LED_PATTERN_RUST` |
| `prj.conf` | Enables GPIO, sets the main stack size, and sets the switch |
| `src/main.c` | Configures the LED and calls `led_pattern()` every 200 ms |
| `src/led_pattern.c` | The original C implementation, kept as the fallback |
| `include/led_logic.h` | Header generated by *cbindgen*; both implementations compile against it |
| `rust/led_logic/` | The Rust crate (`staticlib`) and its `cbindgen.toml` |

## Build the Rust library and generate its header

From this directory:

```sh
cargo build \
    --manifest-path rust/led_logic/Cargo.toml \
    --release \
    --target thumbv7m-none-eabi \
    --target-dir rust/led_logic/target

(cd rust/led_logic && \
    cbindgen --config cbindgen.toml --crate led_logic \
             --output ../../include/led_logic.h)
```

## Build the firmware

Rust implementation (the default):

```sh
west build -p always -b stm32_min_dev@blue -d build .
```

Original C implementation, without editing any file:

```sh
west build -p always -b stm32_min_dev@blue -d build . \
    -- -DCONFIG_LED_PATTERN_RUST=n
```

Check which one you built with `grep LED_PATTERN build/zephyr/.config`.

If the Rust archive is missing while `CONFIG_LED_PATTERN_RUST=y`, CMake stops with `Rust library missing: run the Cargo build command first.`; `west build` never runs Cargo itself.

## Flash

Tested method, using probe-rs:

```sh
probe-rs download --chip STM32F103C8Tx build/zephyr/zephyr.elf
probe-rs reset --chip STM32F103C8Tx
```

**This board's debug wiring has no reset line.** Once Zephyr's idle thread executes `wfi`, the STM32F1 debug port stops answering, and `--connect-under-reset` can't help without NRST. Plain attempts fail with `SwdApWdataError`. The reliable recipe is: **press and release the board's reset button, then start the flash command immediately**, so the probe attaches during the first moments after boot, before the core reaches `wfi`. Holding reset down during flashing does not work on this board.

Getting the timing right by hand can take many tries. A retry loop does the waiting for you; start it, then press and release reset every few seconds until it reports success:

```sh
until probe-rs download --chip STM32F103C8Tx build/zephyr/zephyr.elf; do sleep 0.5; done
probe-rs reset --chip STM32F103C8Tx
```

In our testing this took between 40 and 90 seconds of occasional reset presses.

A probe connection that does carry NRST (as on the NUCLEO boards) doesn't need this.

### About `west flash`

Every flash here is done through probe-rs as shown above. If you try `west flash`, be aware of two problems we hit on the NUCLEO port with the same chip and the same Zephyr version (see `../NUCLEO_STM32F103RBT6/README.md`):

- `west flash --runner openocd` (the Zephyr SDK's bundled OpenOCD) wrote the image but then failed with a `FATAL ERROR` during its post-flash reset.
- On the NUCLEO, an OpenOCD flash ending in `reset` (`program ... verify reset exit`) left the core's debug-enable bit (`C_DEBUGEN`) set. Neither the reset button nor a software reset clears it. On the STM32F1, Zephyr's idle `wfi` then stalls the system tick, so `k_msleep()` never returns and the LED freezes on or off, even though the image verified and the console printed Zephyr's boot banner. A power cycle (unplug and replug the probe's power) recovers it. None of the probe-rs flashes on this Blue Pill showed the problem.

If the LED stays solidly on or off after a successful flash, suspect the debug state before suspecting the code.

## Try it

1. Flash the Rust build: two short flashes, then a pause.
2. Change the Rust match arm in `rust/led_logic/src/lib.rs` from `0 | 2` to `0 | 2 | 4`, rebuild the archive, rebuild and flash: three flashes, without touching any C.
3. Rebuild with `-- -DCONFIG_LED_PATTERN_RUST=n` and flash: back to two flashes, now from `src/led_pattern.c`.
